# Part 1: Define the problem

*Firecracker Lab: Run AI Agents in Isolated MicroVMs*, Part 1 of 5. A talk, no terminal: the problem, two options, why Firecracker, the plan and the roadmap.

[![Part 1: Define the problem](https://img.youtube.com/vi/MAbErIOhTNA/0.jpg)](https://youtu.be/MAbErIOhTNA)

**Before you start:** the earlier Firecracker lab, [Run Your Own MicroVM](../../../3.01-ec2/firecracker-lab-walkthrough.md) ([video](https://youtu.be/65BVRBkMyGU)). The host from that lab (`m7i-flex.large` with nested virtualization, Ubuntu 24.04, Firecracker v1.17.0) is the host for this whole lab.

## The problem

I have a use case where I need to run AI agents, and I need them well isolated from the external environment. I'm not sure yet what the final solution will look like, so this first part is about defining the problem.

We can't always trust the code our agents run. Some of it may be generated by AI and contain mistakes or unsafe operations. Some may come from third-party repositories or packages and could even be malicious. When an agent installs dependencies, builds a project or runs tests, that code gets executed. If something goes wrong, I don't want it to reach the host, access my credentials, or affect other workloads. So the agents run in an isolated sandbox, with limited access to anything outside it.

The question: what kind of isolation do I need, and how should I build it?

## Option 1: Amazon Bedrock AgentCore Runtime

I package my agent, and AgentCore runs it. According to AWS, each session gets its own microVM ([docs](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-sessions.html)). I don't manage a host or choose a kernel. Since June 2026 there are also Lambda MicroVMs, a managed Firecracker VM for untrusted code.

Too high-level for what I want to learn here. With a managed service I'd learn how to use the service, but I wouldn't choose the kernel, build the root filesystem or configure the network myself.

## Option 2: Kata Containers

Kata keeps the container workflow while running each pod inside a small virtual machine. It usually plugs into Kubernetes as a runtime class, and underneath it can use QEMU, Cloud Hypervisor, or Firecracker.

I want to explore Kata, but I don't have Kubernetes running in this lab. Kata can work without Kubernetes; its Kubernetes integration is the interesting part, and that deserves a separate lab. So Kata waits, and this lab uses Firecracker directly.

## Why Firecracker

With Firecracker I do the whole setup myself: the EC2 host, the kernel, the root filesystem, the network. It's the engine under AWS Lambda. Will it be the best fit for production? I don't know yet. But once I've configured the lower layers myself, the layers above make a lot more sense. That's why I chose it for this lab.

Two limits, said up front:

- Firecracker ships a second layer of defense, the **jailer**, which runs the Firecracker process in a chroot with its own namespaces, cgroups and an unprivileged user. It isn't part of the first parts of this lab; it comes in the advanced parts.
- A microVM limits the damage untrusted code can do. It doesn't prove the code is safe.

## The plan, as I see it today

1. Someone opens a pull request on GitHub.
2. A webhook calls a Lambda function.
3. The Lambda tells our EC2 host to start a microVM with an Ubuntu guest.
4. Inside the guest, three agents check the code in a sandbox. In the first version they are scanners, not AI: vulnerable packages, leaked secrets, suspicious code. Each writes a JSON file with its results.
5. The results are collected, and the microVM is destroyed. Every pull request gets a fresh one.

**Lambda and Firecracker.** Lambda is only the trigger. A Lambda function can't host our Firecracker process (no KVM access); Lambda itself runs on Firecracker, but it can't start one for us. The Lambda calls the EC2 host, and the host starts the microVM. One host running one microVM at a time is enough to start with.

**What comes later.** An AI reviewer with a short-lived permission to call a model, scoped to a single job; nothing long-lived goes into the guest. Then a Matrix home server, with a room for every job, where the agents share their findings with people and with other agents. Whether this is the best design is one of the things I want to find out by building it.
